= Module 3: Full Automation — AI-Assisted Remediation
:navtitle: Module 3: Full Automation

*Duration:* 30 minutes

include::partial$lab-access.adoc[]

Module 2 ended with a deliberate limitation: Renovate found one dependency in one repository and asked you to merge it. That works until the day Lightwell publishes forty remediations across sixty repositories, and "ask a human to merge it" stops being a strategy.

This module walks through the same remediation event, handled by the platform instead of by you. An Ansible Orchestrator workflow opens a Snow incident, asks Trusted Profile Analyzer which applications are actually affected, applies each application's own approval policy, and dispatches an AI agent to write the merge request. The pipeline then tests the change and writes the results back into the merge request body, so that when a human *is* asked to decide, they are reading evidence rather than guessing.

You will remediate two of your three applications:

* `benefits-mgmt-app` — internal HR application, risk class `LOW`, policy `auto_approve`. The platform merges it without you.
* `wire-transfer-svc` — payment-critical and PCI-scoped, risk class `HIGH`, policy `needs_approval`. The platform does everything *except* the last step, and then waits for you.

That contrast is the point of the module. Automation is not about removing the human — it is about making sure the human is only interrupted when their judgement is actually worth something.

== Foundations

Before diving into the hands-on steps, this section compares what changes between the quick win approach and the full automation approach, introduces the orchestration pipeline and the two applications you will remediate — one low-risk that merges automatically, one higher-risk that waits for your approval.

[cols="1,2,2",options="header"]
|===
| Stage | Quick Win (Module 2) | Full Automation (this module)

| Trigger
| Renovate polls the artifact manager on a schedule
| The artifact manager fires a `component CREATED` webhook the moment the artifact lands

| Who finds the affected apps
| Renovate reads one repository's `pom.xml`
| TPA is queried for every SBOM containing the component

| Who writes the fix
| Renovate's regex manager
| The `impact-analyzer` AI agent (OpenCode)

| What the merge request says
| A one-line version bump
| CVE, CVSS, risk class, and a validation table filled in by the pipeline

| Who approves
| Always you
| Per-app policy — `auto_approve` or `needs_approval`

| Audit trail
| Git history only
| A Snow incident, commented at every stage

| Build, sign, deploy
| Shared — Tekton, OCI registry, ArgoCD, TPA
| Shared — identical
|===

The back half of both paths is the same. Full automation only replaces *who decides what to change and whether it may ship*.

== The Orchestrated Pipeline

Event-Driven Ansible is deliberately thin here. It is a sensor: it recognises the `.rhlw` artifact event and triggers a job template, which posts to an Ansible Orchestrator webhook. Everything after that is a node on an Orchestrator canvas, recorded as it runs.

Your project contains *three* workflows, not one, and the split is the first thing worth understanding:

[cols="1,3",options="header"]
|===
| Workflow | Runs when

| *Lightwell Remediation — Start*
| A remediated artifact is published. Ends when the merge requests are ready.

| *— Merged*
| A merge request is merged — by you or by the Orchestrator. Follows the build through.

| *— Deploy*
| ArgoCD reports the application healthy. Closes the incident out.
|===

They are separate because the Orchestrator cannot pause a run and resume it on an outside event. Rather than hold a job open for the hours a human review might take, each stage is its own short execution, woken by a webhook. The Snow incident is what ties them back into one story.

.Start: from artifact to reviewable merge request
[mermaid]
----

  EDA["Event-Driven Ansible<br/>(sensor only)"]
  PREP["Prepare Remediation<br/>SNOW parent · query TPA · classify · child incidents"]
  LOOP{{"For each affected app"}}
  IMP["Impact Analyzer<br/>AI agent opens the MR"]
  VER["MR Verifier"]
  APPR{"Auto-approve?"}
  AUTO["Merge MR<br/>(auto-approved)"]
  WAIT["SNOW — awaiting<br/>GitLab merge"]
  HUMAN(["Human merges<br/>in GitLab"])
  NX --> EDA --> PREP --> LOOP

  APPR -->|auto_approve| AUTO

All the preparation — opening the parent incident, asking TPA which applications contain the component, classifying each against its policy, raising a child incident per application — is a single *Prepare Remediation* node. It is one Ansible job running several plays, so the canvas shows you the decision points rather than the plumbing.

The merge — by the Orchestrator or by you — is where the full automation path rejoins the quick win path:

.Merged and Deploy: two more short runs

----

  LC1["Merged: SNOW — MR merged"]
  POLL["Poll Build Status<br/>watches PaC commit status"]
  PIPE["Tekton build-push-to-main<br/>build · SBOM · sign · push · promote"]

  MG --> PIPE

  POLL --> LC2

The *Merged* workflow does not get a webhook when the build finishes — Tekton does not send one. Instead it polls the GitLab commit status that Pipelines-as-Code already mirrors from the PipelineRun. That is why one Merged execution can run for several minutes: it is watching your build.

NOTE: The `report-generator-app` you remediated in Module 2 never enters this loop. Its policy marks Renovate as the remediation owner, so the classify step records it and skips it. Two tools, one portfolio, no collisions.

== Two Applications, Two Policies

Each repository carries a `.lightwell/policy.json` file. It is the primary control that decides whether a human is interrupted — but it is not the only one. If any step in the merge request pipeline fails (unit tests, regression scan, licence compliance), the merge is blocked regardless of policy, and the change requires human review:

[cols="2,1,1,3",options="header"]
|===
| Application | `remediation_owner` | `approval` | `riskClass` and why

| `wire-transfer-svc`
| `ao`
| `needs_approval`
| `HIGH` — payment-critical, PCI-scoped system

| `benefits-mgmt-app`
| `ao`
| `auto_approve`
| `LOW` — internal HR application, no regulated data

| `report-generator-app`
| `renovate`
| —
| `LOW` — internal reporting tool, no regulated data
|===

The policy travels with the code, in the repository, reviewed like any other change. There is no approval matrix in a wiki that nobody has opened since the last audit.

TIP: Open `.lightwell/policy.json` in `acme-{guid}/wire-transfer-svc` in https://gitlab-gitlab.{openshift_cluster_ingress_domain}[GitLab^] before you start. It is four lines, and it is the entire governance model for this lab.

== The Incident Opens Before the Change Does

Look at the order again. Opening the parent incident is the *first* thing *Prepare Remediation* does — before TPA is queried, before anything is classified, before a single line of anyone's `pom.xml` is read. The platform raises the ticket and then does the work, which is the opposite of how most automation behaves.

Switch to the *Snow* tab on the right (or https://snow-mock-snow-{guid}.{openshift_cluster_ingress_domain}[open it in a new tab^]) — no login required. Your incident is at the top of the list, with the most recent state.

What you are looking at is a small hierarchy, not one ticket:

* A *parent* incident for the remediation event itself — one artifact, one Lightwell publication, one thread to follow.
* A *child* incident per affected application, created straight after classify, once the Orchestrator knows which applications are genuinely in scope.

The children are where the detail goes. Each application's loop iteration comments on its own child as it completes — merge request opened, verifier passed, awaiting merge — so two applications remediated from one event do not interleave their history into a single unreadable timeline. The parent gets short milestone notes with links down into the children, and nothing else. An operator reads the parent to find out *where things are*, and opens a child to find out *what happened*.

The comments are not just prose, either. Open one and the merge request, the pipeline run and (later) the ArgoCD application and the running route are all clickable, so the ticket is a working console rather than a transcript.

Your two incidents are at the top of the list, both raised by *Lightwell AO* (Ansible Orchestrator). Open the parent — the one whose description starts with *remediate*:

image::m3-snow-parent-incident.png["The parent incident, showing the blast-radius classification and the child tickets it opened",link=_images/m3-snow-parent-incident.png,window=_images]

== The Merge Request the Agent Wrote

In the loop, the Orchestrator tasks the `impact-analyzer` agent with creating the fix. The agent reads the application's `pom.xml`, bumps the dependency to the remediated `.rhlw` version, pushes a branch, and opens a merge request.

Switch to the *GitLab* tab on the right (or https://gitlab-gitlab.{openshift_cluster_ingress_domain}[open it in a new tab^]) and go to `acme-{guid}/benefits-mgmt-app` → *Merge requests*. The title follows a fixed shape:

[source,text]
----
[LW] 🟢 Bump commons-text to 1.9.rhlw-00001 to fix CVE-2022-42889
----

Yours will name the dependency you just published, with its own `.rhlw` number.

The coloured dot is the *application's* Acme Inc. risk class, not the severity of the CVE. That distinction is easy to miss and worth pausing on: `CVE-2022-42889` is a critical-severity flaw, yet this merge request is green, because `benefits-mgmt-app` is a low-risk application and the fix is therefore allowed to merge itself. The `wire-transfer-svc` merge request later in this module carries a 🔴 for the opposite reason. A reviewer scanning twenty merge requests is triaging by *what the change can break*, not by how frightening the CVE sounds.

The diff itself is almost boring — the same single-line `pom.xml` change Renovate made in Module 2. The interesting part is the description, which is the artifact a human is actually expected to read:

== The Pipeline Fills in the Validation Table

The merge request is created before any testing has happened, so every row in the *Automated Validation* table starts as `Pending`. A Pipelines-as-Code pipeline, `build-pull-request`, runs against the open merge request, executes `mvn verify` together with the CycloneDX SBOM plugin, and then rewrites that one section of the description with real results.

=== While You Wait: Following the Checks

Scroll to the bottom of the merge request. For the next minute or two it looks like this:

image::m3-mr-merge-blocked.png["The merge request widget showing a running pipeline and Merge blocked: Pipeline must succeed",link=_images/m3-mr-merge-blocked.png,window=_images]

*Merge blocked: 1 check failed — Pipeline must succeed.* Nothing has gone wrong. The pipeline is still running, and GitLab will not let anyone merge — you, a colleague, or the Orchestrator — until it reports success. The wording is unfortunate: "1 check failed" here means "the required check has not passed yet", not "a test broke".

This is the whole point of the gate. Evidence arrives *before* the decision, not after it. Notice also *Set to auto-merge*: you can commit to the merge now and let GitLab carry it out the moment the checks pass. You are never asked to choose between waiting and trusting.

Rather than watch a spinner, follow what is actually happening. Click *Pipeline #<n>* in that widget:

image::m3-gitlab-pipeline-running.png["The GitLab pipeline page showing a single external stage running Pipelines as Code CI / build-pull-request",link=_images/m3-gitlab-pipeline-running.png,window=_images]

One stage, named *external*, running `Pipelines as Code CI / build-pull-request`. "External" is the interesting word: there is no `.gitlab-ci.yml` in this repository and no GitLab runner involved. The build is executing on OpenShift as a Tekton `PipelineRun`, and Pipelines-as-Code is mirroring its status back here so that GitLab has something to gate on. The merge gate and the build are deliberately in different systems.

To watch the build itself, open the *OpenShift Console* tab, navigate to *Pipelines* → *Pipelines* → *PipelineRuns*, and select the `build-{guid}` project:

image::m3-tekton-pipelinerun.png["The PipelineRun details view in the OpenShift console showing fetch-source, run-tests, baseline-tests and report-validation",link=_images/m3-tekton-pipelinerun.png,window=_images]

Four tasks, and they map directly onto the table you are waiting for:

* `fetch-source` — clones the merge request branch
* `run-tests` — `mvn verify` plus the CycloneDX SBOM, against the *remediated* dependency
* `baseline-tests` — the same tests again against the dependency version you are replacing. This is what makes *Regression scan* a comparison rather than an assumption, and it is why the pipeline takes roughly twice as long as a plain build
* `report-validation` — writes the results into the merge request, and fails the pipeline if any row is not green

That last task is the one holding your Merge button. Once it passes, the gate opens.

Refresh the merge request and the table will have filled in:

[cols="2,3",options="header"]
|===
| Check | What it actually measures

| Acme Inc. Risk Class
| The `riskClass` from the application's policy file

| Binary signature verification
| An *integrity* check — the published JAR is compared against the checksum the artifact manager recorded for it. The lab mirror ships no detached GPG signature, so this is not a cryptographic signature check and is labelled accordingly.

| SBOM integrity
| A CycloneDX SBOM is generated in the same build and asserted to list the bumped coordinate

| Unit tests
| `surefire` results from `mvn verify`

| Integration tests
| `failsafe` results from the same run

| Dependency compatibility
| Asserts that what the `pom.xml` declares is what the build actually resolved

| Regression scan
| Re-runs the whole suite against the target branch's `pom.xml` and compares the result test by test, so a test that was already failing before the bump is not blamed on it

| License compliance
| Compares the licence declared by the base POM against the remediated POM, normalised so that equivalent phrasings do not raise a false alarm
|===

image::m3-mr-validation-filled.png["The same table after build-pull-request has run, with every check Passed",link=_images/m3-mr-validation-filled.png,window=_images]

IMPORTANT: Every one of those rows is measured. Nothing is ever reported green without having been measured, which is the only reason the table is worth putting in front of a reviewer at all — and a row that *could not* be established says so, rather than quietly reading `Passed`.

The regression scan is why this pipeline takes about twice as long as you might expect: it builds the application a second time against the dependency version you are replacing, so that "no behavioural change" is a comparison rather than an assumption. Roughly ninety seconds in total.

== The Low-Risk Application Merges Itself

Back on the Orchestrator canvas, the *MR Verifier* node confirms the merge request is healthy and every check reported, then the *Auto-approve?* condition reads the approval value that travelled with the application's own policy.

For `benefits-mgmt-app` that value is `auto_approve`, so the canvas takes the green branch to *Merge MR (auto-approved)*. The Orchestrator marks the merge request ready and merges it. No human is asked, and no human is notified. The child incident gets a comment recording the merge, and the loop moves on to the next application.

Switch back to the *GitLab* tab and open the merge request again. The block you watched earlier has cleared and the merge has already happened — performed by the automation account, with you never touching it:

image::m3-mr-auto-merged.png["The merge request showing the branch pipeline passed, then Merged by Administrator, then the pipeline on main",link=_images/m3-mr-auto-merged.png,window=_images]

Read those three panels top to bottom, because they are in causal order:

. *Pipeline #60 passed* on `update-artifact-1.9…` — the branch build finished and every row of the table went green. Only now is merging possible at all.
. *Merged by Administrator* — the Orchestrator took the gate the moment it opened.
. *Pipeline #61 passed* on `main` — merging started a second, different build: the one that produces the image you will deploy.

Check the timestamps while you are there. The merge happened roughly two minutes after the request was opened, not seconds — the Orchestrator was waiting for `build-pull-request` to report before it merged. It could not have jumped that queue even if it had tried.

This is the volume case, and it is the whole economic argument for the platform. An internal HR application, a compatible rebuild of a library, every automated check green: there is no decision here that a person adds value to, so no person is asked. Multiply that by forty remediations a week and the time saved is not the merge click — it is the context switch that surrounds it.

[NOTE]
====
The decision is made from `.lightwell/policy.json` in the application's own repository, and it fails closed. If that file is missing, unreadable or malformed, the Orchestrator treats the application as `needs_approval` and routes it to a human. Nothing merges itself by accident.
====

== Build, Sign, Promote, Deploy

Merging to `main` starts the build pipeline. Switch to the *OpenShift Console* tab on the right (or https://console-openshift-console.{openshift_cluster_ingress_domain}[open it in a new tab^]), navigate to *Pipelines* → *Pipelines*, select the *PipelineRuns* tab, and make sure the `build-{guid}` namespace is selected. You should see the run for `benefits-mgmt-app`:

. *Build* — compiles the application against the remediated dependency
. *Generate SBOM* — CycloneDX SBOM, uploaded to your TPA instance
. *Sign* — Tekton Chains signs the image via Trusted Artifact Signer, with no long-lived signing key
. *Push* — the signed image goes to the OCI registry
. *Promote* — `promote-to-deployment-repo` bumps the application's `imageTag` in the `acme-deployment` repository

The task graph has one more box than the list above: `run-tests` and `maven-build` are separate tasks, and there is no `sign` task at all. == The Judgement Call

On the canvas, the *Auto-approve?* condition does not see `auto_approve`, so it takes the other branch: a comment on the child incident recording that the merge request is ready and *awaiting a GitLab merge*. Then the execution ends.

Read that again, because it is easy to misread as a failure. The Orchestrator has not crashed, timed out, or parked a job that is burning a worker somewhere. It has done everything it is permitted to do and stopped. The merge request is open in GitLab with your name on it, and nothing further happens in this entire platform until a person acts.

Open the *Lightwell Remediation — Start* run for this trigger and zoom in on the right-hand side of the canvas. The `False` branch of *Auto-approve?* carries the green tick, and the path onward to *Merge GitLab MR (auto_approve)* is dashed, meaning it was never taken:

image::m3-hr-auto-approve-false.png["The Auto-approve? condition on the Orchestrator canvas with its False branch ticked and highlighted; the auto-merge path is dashed and the solid path leads to SNOW — MR ready",link=_images/m3-hr-auto-approve-false.png,window=_images]

Compare that with the low-risk run earlier, where the same condition ticked `True` and ran straight into *Merge GitLab MR*. The green tick marks the branch that was taken — it is a record of a decision, not an error.

[IMPORTANT]
====
*The pause lives in GitLab, not in the Orchestrator.* There is no approve button on the canvas and no task in a queue waiting for you to tick it. The human gate is the merge request itself — the artifact that actually carries the evidence — rather than a prompt in an automation tool that quotes a ticket number at you.
====

Check Snow first. The child incident for `wire-transfer-svc` records that the merge request is ready and hands the decision to you — *please review and merge in GitLab when you are satisfied; CI/CD will continue from there*:

image::m3-hr-snow-awaiting-merge.png["The wire-transfer-svc child incident showing the remediation is ready for review under the needs_approval policy",link=_images/m3-hr-snow-awaiting-merge.png,window=_images]

Now go and read the merge request in `acme-{guid}/wire-transfer-svc`. Everything you need is in one page:

* The diff — a single version bump in `pom.xml`, the upstream version unchanged
* The CVE and its CVSS score, pulled from TPA rather than from the model
* The validation table — unit tests, integration tests, SBOM integrity, licence compliance and dependency compatibility, all measured on this exact change
* The risk class, `HIGH`, with its rationale: payment-critical, PCI-scoped
* The recommended action, which says *human review required* precisely because the risk class is `HIGH` — not because anything failed

Read that last point again, because it is the whole argument. Every automated check passed. The platform still refused to merge it. The policy says that on a system that moves customer money a person signs off even on a change that looks perfect, and the platform is not allowed to talk itself out of that — not even with a full table of green ticks to point at.

Note the *Recommended Action* block at the bottom. For `benefits-mgmt-app` it said the change was safe to take. Here it reads:

🔍 *Requires human review before merge.* A security or DevSecOps engineer should review the patch diff. Risk class *HIGH* requires review regardless of automated results.

Switch to the *TPA* tab on the right (or https://tpa-{guid}.{openshift_cluster_ingress_domain}[open it in a new tab^]). Sign in through SSO with `{user}` / `{password}` if needed. The dashboard tells you how much it is holding for this tenant, and when the last SBOM arrived — which should be the build you just watched:

In the left-hand navigation, expand *SBOMs* and choose *All SBOMs*:

| Application | Build | Dependencies | Vulnerabilities

The two tell different stories, and the difference is worth understanding.

For `benefits-mgmt-app` the headline number moves: two vulnerabilities fewer, one of them critical, and one dependency fewer. The vulnerable `commons-text` is gone and the `.rhlw` build stands in its place.

For `wire-transfer-svc` the total does not move at all. It stays at 90, with one critical becoming one high. That is not a failed remediation — it is an honest picture of a payment system carrying 238 dependencies and a long tail of known issues that this one fix was never going to touch. The build changed; the backlog did not.

[IMPORTANT]
====
*A count is not proof, and this is the clearest place in the lab to see why.* TPA can only subtract advisories it actually holds. If a component has no advisory in this tenant's dataset, the number is unchanged even though the dependency genuinely changed — and on an application with 90 findings, a single remediation barely registers.

The reliable evidence is the SBOM *contents*: open either build and search the component list for the coordinate. The vulnerable version is absent and the `.rhlw` build is present. That is a fact about the software. The count is a summary of what the scanner happens to know, which is a different thing — and worth remembering the next time a dashboard is offered as evidence.
====

Notice what none of this required: nobody wrote a report and nobody updated a spreadsheet.

The verification is not a separate exercise bolted on at the end. The pipeline uploaded the SBOM as part of the build, which means the evidence for the *next* remediation is already in place. That is what makes the loop a loop.

== The Incident Closes Last

Switch back to the *Snow* tab on the right (or https://snow-mock-snow-{guid}.{openshift_cluster_ingress_domain}[open it in a new tab^]).

The parent incident is now *Resolved*. Read its thread from the top — it is deliberately short, a sequence of milestones with links down into the children:

. The incident was raised the moment the artifact manager announced the artifact — before anything was known about who was affected
. Child tickets were opened, one per application TPA said was genuinely affected
. Each application reached a reviewable merge request
. Merge, build and deploy were each noted as they landed
. The parent moved to *Resolved* once ArgoCD reported the application Healthy

Now open a child. That is where the work actually is: the merge request link, the CVE, the verifier outcome, the pipeline run, the ArgoCD application and the route the fixed code is now serving on. The parent tells an operator where things stand; the child tells them what happened.

Notice what resolved it. Not the merge, and not a green pipeline — the *deploy*. `SNOW finalize` only runs in the Deploy workflow, so the ticket stays open until the remediated code is actually running. A build that passes and never ships does not close anything.

That is also why three workflows rather than one long-running job. The Start run ends when the merge requests are ready; merge and deploy arrive later as webhooks and start their own short executions. The incident is what stitches them back into a single story — which is precisely the job a ticket is supposed to do.

NOTE: The child incidents stay open. Only the parent is resolved today; per-application close on deploy success is not wired up. If you are demonstrating this to an auditor, show them the parent and let them click down.

[TIP]
====
This is the slide that usually lands in front of a risk or compliance team. Nobody had to be asked for the evidence, and nobody had to assemble it afterwards. The incident was open before the change existed, it accumulated every decision and measurement along the way, and it closed when the fix was live — produced entirely as a side effect of doing the work.
====

== Summary

You have just run the *Full Automation* path end to end:

. You published a remediated artifact; the artifact manager raised a `component CREATED` event
. Event-Driven Ansible acted as a sensor and started the Orchestrator workflow
. The Orchestrator opened a Snow incident before proposing any change
. TPA answered which applications were genuinely affected, from SBOM data
. Each application was classified against its own `.lightwell/policy.json`
. The `impact-analyzer` agent opened a merge request carrying CVE data, risk class and a validation table
. The `build-pull-request` pipeline tested the change and wrote the real results back into that table
. `benefits-mgmt-app` was auto-approved and merged by the Orchestrator, without you
. `wire-transfer-svc` passed every check, and its merge request still said human review was required, so it waited for you to merge it in GitLab
. Both were built, signed, promoted and deployed by the same pipeline and ArgoCD
. The parent incident resolved once ArgoCD reported the deployment Healthy, carrying a complete, timestamped trail

=== What This Actually Buys You

The difference from the quick win path is not "AI wrote the merge request". It is three things:

* *Scope* — the system knows which applications contain the component, because it asked TPA rather than scanning a single repository.
* *Evidence* — by the time a human looks at the change, the tests have run and the results are in the merge request. The reviewer reads measurements, not promises.
* *Proportionality* — attention is spent where it changes the outcome. An internal HR application merges itself. A PCI-scoped payment service does not, and no amount of green ticks changes that.

Scale is what makes this necessary. One remediation a week is a Renovate problem. Forty a week across sixty repositories, each needing a risk judgement and an audit trail, is an orchestration problem — and the only way a human stays in the loop at that volume is if the loop stops bothering them about `benefits-mgmt-app`.
