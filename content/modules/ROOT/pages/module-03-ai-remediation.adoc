= Module 3: Full Automation — AI-Assisted Remediation
:navtitle: Module 3: Full Automation

*Duration:* 30 minutes

include::partial$lab-access.adoc[]

Module 2 ended with a deliberate limitation: Renovate found one dependency in one repository and asked you to merge it. That works until Lightwell publishes a rebuild that several applications depend on, and someone still has to know which repositories are affected.

This module walks through that event on your OpenShift cluster. Publishing a `.rhlw` artifact starts one Tekton run, `lightwell-intake`. That run opens a Snow incident, asks Trusted Profile Analyzer which applications contain the component, and reads each application's `.lightwell/policy.json`. For every application the platform owns, it creates a Renovate job. Renovate opens the merge request and changes only the dependency version. `build-pull-request` tests that change. You merge it. `build-push-to-main` builds the image, and the incident closes when Argo CD is healthy.

You will remediate two applications:

* `benefits-mgmt-app` — internal HR application, risk class `LOW`, approval `auto_approve`. The policy is recorded on the merge request. It does not merge the request.
* `wire-transfer-svc` — payment-critical and PCI-scoped, risk class `HIGH`, approval `needs_approval`. The merge request says a person should review it. You merge this one too.

`report-generator-app` stays on the Module 2 path. Its policy owner is `renovate`, so intake names it in a comment and does not create a job for it.

== Foundations

Three ideas run through this module:

* *Evidence before decision* — the pipeline fills in the validation table before GitLab enables Merge. You read measured results.
* *The policy classifies the change* — `auto_approve` and `needs_approval` change the recommended action on the merge request. Neither value merges it.
* *Verify the artifact, not the dashboard* — the SBOM contents are the fact. Vulnerability counts depend on what the scanner knows.

[cols="1,2,2",options="header"]
|===
| Stage | Quick Win (Module 2) | Full Automation (this module)

| Trigger
| Renovate polls the artifact manager on a schedule
| The artifact manager fires a `component CREATED` webhook when the artifact is published

| Who finds the affected apps
| Renovate reads one repository's `pom.xml`
| `lightwell-intake` asks TPA which SBOMs contain the component

| Who writes the fix
| Renovate's regex manager
| Renovate bumps `pom.xml`. OpenCode edits application code only when the regression scan shows a difference

| What the merge request says
| A one-line version bump
| The bumped coordinate, the application's risk class, and a validation table filled in by the pipeline

| Who approves
| Always you
| Always you. The policy says how carefully to read the request

| Audit trail
| Git history only
| A Snow incident, commented when the rollout is healthy or when it fails

| Build, sign, deploy
| Shared — Tekton, OCI registry, Argo CD, TPA
| The same `build-push-to-main` pipeline, plus a wait until Argo CD is healthy
|===

== How the Pipeline Is Organized

Three Tekton runs do the work. They are separate because they start from different events.

[cols="1,3",options="header"]
|===
| Run | Runs when

| `lightwell-intake`
| Nexus reports a component whose version contains `rhlw-`. One run per published coordinate. It does not clone an application repository.

| `build-pull-request`
| Renovate opens or updates a merge request. It tests the bump and, only when test outcomes differ from the base branch, asks OpenCode to adapt application code.

| `build-push-to-main`
| You merge to `main`. It builds the image, uploads the SBOM, commits the image tag, and waits until `acme-apps-{guid}` is Synced and Healthy.
|===

.From a published artifact to a running pod
[mermaid, width="100%"]
----
flowchart TD
  NX["Nexus component CREATED"]
  IN["lightwell-intake<br/>Snow parent, TPA, policy, RenovateJob"]
  MR["Renovate merge request<br/>pom.xml only"]
  PR["build-pull-request<br/>tests, adapt only on a difference"]
  YOU(["You merge in GitLab"])
  MAIN["build-push-to-main<br/>image, SBOM, promote"]
  ARGO["Argo CD Synced and Healthy"]
  SNOW["Snow child resolved<br/>parent resolved when every child is"]
  NX --> IN --> MR --> PR --> YOU --> MAIN --> ARGO --> SNOW
  style YOU fill:#f8d7da,stroke:#b02a37,stroke-width:2px
----

`report-generator-app` does not enter this flow. Intake records the skip on the parent incident and leaves that repository to the Renovate schedule you configured in Module 2.

== Two Applications, Two Policies

Each application repository carries a `.lightwell/policy.json`. The `remediation_owner` value `ao` means this Tekton path. The `approval` value is recorded on the merge request and does not merge it. A failed `build-pull-request` keeps the Merge button disabled either way.

| `wire-transfer-svc`
| `ao`

| `benefits-mgmt-app`
| `ao`

| `LOW` — internal HR application, no regulated data

| `report-generator-app`
| `renovate`

== Publish a Low-Risk Rebuild

Publish a remediated build of a dependency that `benefits-mgmt-app` declares in its `pom.xml`.

. Run:
+
[source,bash,role=execute,subs=attributes+]
----
curl -sSL https://showroom-{user}-showroom.{openshift_cluster_ingress_domain}/modules/_attachments/publish-remediation.sh \
  | bash -s -- \
  org.apache.commons:commons-text:1.9 \
  rhlw-00001 \
  "Apache Commons Text"
----

. The script should end with `=== Remediation published ===` and the coordinate `org.apache.commons:commons-text:1.9.rhlw-00001`.

Publishing the coordinate once is what fires the webhook. Publishing the same group, artifact, and version again does not. If you need to run this module twice, increment the suffix (`rhlw-00002`).

== Watch the Intake Run

. In the OpenShift Console, open *Pipelines* → *PipelineRuns* and select the project `build-{guid}`.
. Open the new `lightwell-intake` run. It has one task, `intake`.
. When it succeeds, the log names the parent incident and the Renovate job for each platform-owned application TPA returned. A `renovate` owner is listed as skipped and has no job.

== Review the Merge Request

Renovate opens the merge request. The title starts with `[Lightwell]` and names the dependency.

. In GitLab, open `acme-{guid}/benefits-mgmt-app` → *Merge requests*.
. Open the request. The description records the old and new versions and the risk class from `.lightwell/policy.json`. `auto_approve` is in that row. It is not an instruction to merge.
. Open *Changes*. The diff is the `pom.xml` version bump. Renovate does not edit application source.

== Watch the Validation Checks

`build-pull-request` runs on the merge request.

. At the bottom of the merge request, GitLab shows *Merge blocked* while the pipeline is running. That is the gate. The button stays disabled until the pipeline succeeds.
+
image::m3-mr-merge-blocked.png["The merge request widget showing a running pipeline and Merge blocked: Pipeline must succeed",link=_images/m3-mr-merge-blocked.png,window=_images]

. Open the pipeline link. The stage is *external*: `Pipelines as Code CI / build-pull-request`. There is no `.gitlab-ci.yml` and no GitLab runner.
+
image::m3-gitlab-pipeline-running.png["The GitLab pipeline page showing a single external stage running Pipelines as Code CI / build-pull-request",link=_images/m3-gitlab-pipeline-running.png,window=_images]

. In the OpenShift Console, project `build-{guid}`, open that PipelineRun. A clean comparison shows:
+
.. `fetch-source` — clones the merge request branch
.. `run-tests` — `mvn verify` and the CycloneDX SBOM against the bumped dependency
.. `baseline-tests` — the same tests against the base branch's `pom.xml`, and a count of outcomes that differ
.. `adapt` — present in the pipeline, and skipped when that count is zero
.. `report-validation` — writes the table and fails the run unless every measured row passed

`adapt` runs only when at least one test outcome differs. It calls the OpenCode server in `sdlc-{guid}`, waits until the session is idle, and pushes a commit with the pipeline token. That commit may contain only `src/main/`, `src/test/`, and `REMEDIATION.md`. A `pom.xml` change is refused and the task fails. This commons-text rebuild is a compatible bump, so expect `adapt` to be skipped.

. Refresh the merge request. The validation table should be filled in.
+
[cols="2,3",options="header"]
|===
| Check | What it measures

| Acme Inc. Risk Class
| `riskClass` from the policy file. A classification, not a measured check

| Binary signature verification
| The published JAR matches the checksum the artifact manager recorded

| SBOM integrity
| The generated CycloneDX SBOM lists the bumped coordinate

| Unit tests
| Surefire results from `mvn verify`

| Integration tests
| Failsafe results from the same run

| Dependency compatibility
| `pom.xml` declares the version the build resolved

| Regression scan
| Per-test comparison against the base branch's dependency

| License compliance
| The remediated POM's license compared with the base POM
|===

image::m3-mr-validation-filled.png["The validation table after build-pull-request, with every check Passed",link=_images/m3-mr-validation-filled.png,window=_images]

A row that is pending, warning, or failed keeps the pipeline red. GitLab will not enable Merge.

== Build and Deploy

Merging to `main` starts `build-push-to-main`.

. In *PipelineRuns* for `build-{guid}`, open the new run for `benefits-mgmt-app`. Confirm these tasks:
+
.. `maven-build` — compiles against the remediated dependency
.. `build-image` — pushes the image. Tekton Chains signs it after the run; the signature is the shield on the PipelineRun, not a task in the graph
.. `generate-upload-sbom` — uploads the CycloneDX SBOM to TPA
.. `promote-to-deployment-repo` — commits the image tag in `acme-deployment`
.. `wait-for-argo` — waits until `acme-apps-{guid}` is Synced and Healthy on that commit
+
image::m3-pipeline-run.png["The PipelineRun for build-push-to-main through promote-to-deployment-repo",link=_images/m3-pipeline-run.png,window=_images]

. Open Argo CD at https://openshift-gitops-server-openshift-gitops.{openshift_cluster_ingress_domain}[the GitOps console^] and choose *Log in via OpenShift*. Allow the `user:info` permission the first time.
+
image::m3-argocd-authorize.png["The OpenShift Authorize Access screen for the Argo CD login",link=_images/m3-argocd-authorize.png,window=_images]

. Open `acme-apps-{guid}`. *Sync Status* should be `Synced` and *Health* should be `Healthy`. The commit message names `benefits-mgmt-app`.
+
image::argocd-acme-apps-synced.png["The Argo CD application for acme-apps, Synced, with the promote commit",link=_images/argocd-acme-apps-synced.png,window=_images]

If the application has not synced yet, click *Sync*. The poll in the pipeline waits for the same status.

. Return to *Topology* in `{user}-app`. The deployment is still `benefits-mgmt-app-prod`. The pod name is new. Open the *Route* and confirm the application responds.

== Confirm the Incidents Are Resolved

. Return to Snow.
. Open each parent from this module. A parent is *Resolved* only after every one of its children is resolved.
. Open a child. A healthy rollout resolved it. A failed `build-push-to-main` or a rollout that never became healthy left it open and added a comment.

The incident closes when the application is running, not when the merge request is green.

== Summary

. You published a remediated artifact and Nexus raised `component CREATED`.
. `lightwell-intake` opened a Snow parent, queried TPA, read `.lightwell/policy.json`, and created a Renovate job for each platform-owned application.
. Renovate opened a merge request that changes `pom.xml`.
. `build-pull-request` tested the change, skipped `adapt` when the regression scan found no difference, and failed the run unless every measured row passed.
. You merged `benefits-mgmt-app` and `wire-transfer-svc` yourself. `auto_approve` did not merge either request.
. `build-push-to-main` built, signed, promoted, and waited until Argo CD was Synced and Healthy.
. The child incident resolved on that healthy rollout. The parent resolved when it had no open children.

=== Key Takeaways

* *Scope* — intake asks TPA which applications contain the component.
* *Evidence* — the validation table is filled by the pipeline before Merge is enabled.
* *A person merges* — the policy changes the recommended action. It does not click Merge.
* *The ticket follows the rollout* — a green pipeline that never becomes a healthy deployment leaves the incident open.
