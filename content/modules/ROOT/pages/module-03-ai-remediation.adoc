= Module 3: Full Automation — AI-Driven Remediation
:navtitle: Module 3: AI Remediation (Path 2)

[WARNING]
====
This module is a *work in progress*. Steps and screenshots may change before the final version.
====

*Duration:* 30 minutes

Module 2 ended with a deliberate limitation: Renovate found one dependency in one repository and asked you to merge it. That works until the day Lightwell publishes forty remediations across sixty repositories, and "ask a human to merge it" stops being a strategy.

This module walks through *Path 2* — the same remediation event, handled by the platform instead of by you. An Automation Orchestrator workflow opens a ServiceNow incident, asks Trusted Profile Analyzer which applications are actually affected, applies each application's own approval policy, and dispatches an AI agent to write the merge request. The pipeline then tests the change and writes the results back into the merge request body, so that when a human *is* asked to decide, they are reading evidence rather than guessing.

You will remediate two of your three applications:

* `benefits-mgmt-app` — internal HR application, risk class `LOW`, policy `auto_approve`. The platform merges it without you.
* `wire-transfer-svc` — payment-critical and PCI-scoped, risk class `HIGH`, policy `needs_approval`. The platform does everything *except* the last step, and then waits for you.

That contrast is the point of the module. Automation is not about removing the human — it is about making sure the human is only interrupted when their judgement is actually worth something.

== What Changes Compared to Path 1

[cols="1,2,2",options="header"]
|===
| Stage | Path 1 (Module 2) | Path 2 (this module)

| Trigger
| Renovate polls Nexus on a schedule
| Nexus fires a `component CREATED` webhook the moment the artifact lands

| Who finds the affected apps
| Renovate reads one repository's `pom.xml`
| TPA is queried for every SBOM containing the component

| Who writes the fix
| Renovate's regex manager
| The `impact-analyzer` AI agent (OpenCode)

| What the merge request says
| A one-line version bump
| CVE, CVSS, risk class, and a validation table filled in by the pipeline

| Who approves
| Always you
| Per-app policy — `auto_approve` or `needs_approval`

| Audit trail
| Git history only
| A ServiceNow incident, commented at every stage

| Build, sign, deploy
| Shared — Tekton, Nexus OCI, ArgoCD, TPA
| Shared — identical
|===

The back half of both paths is the same. Path 2 only replaces *who decides what to change and whether it may ship*.

== The Orchestrated Pipeline

Event-Driven Ansible is deliberately thin here. It is a sensor: it recognises the `.rhlw` artifact event and launches one job template, `SDLC Start Orchestrator`, which posts to the Automation Orchestrator webhook. Everything after that is a node on the Orchestrator canvas, which means the whole flow is visible in one place and every step is recorded as it runs.

== Two Applications, Two Policies

Each repository carries a `.lightwell/policy.json` file. It is the only thing that decides whether a human is interrupted:

[cols="2,1,1,3",options="header"]
|===
| Application | `remediation_owner` | `approval` | `riskClass` and why

| `wire-transfer-svc`
| `ao`
| `needs_approval`
| `HIGH` — payment-critical, PCI-scoped system

| `benefits-mgmt-app`
| `ao`
| `auto_approve`
| `LOW` — internal HR application, no regulated data

| `report-generator-app`
| `renovate`
| —
| `LOW` — internal reporting tool, no regulated data
|===

The policy travels with the code, in the repository, reviewed like any other change. There is no approval matrix in a wiki that nobody has opened since the last audit.

TIP: Open `.lightwell/policy.json` in `acme-{guid}/wire-transfer-svc` in https://gitlab-gitlab.{openshift_cluster_ingress_domain}[GitLab^] before you start. It is four lines, and it is the entire governance model for this lab.

== The Incident Opens Before the Change Does

Look at the order of the nodes again. *Create parent SNOW incident* is the first thing on the canvas — before TPA is queried, before anything is classified, before a single line of anyone's `pom.xml` is read. The platform raises the ticket and then does the work, which is the opposite of how most automation behaves.

Switch to the https://snow-mock-snow-{guid}.{openshift_cluster_ingress_domain}[ServiceNow mock^] (no login required). Your incident is at the top of the list, with the most recent state.

What you are looking at is a small hierarchy, not one ticket:

* A *parent* incident for the remediation event itself — one artifact, one Lightwell publication, one thread to follow.
* A *child* incident per affected application, created straight after classify, once the Orchestrator knows which applications are genuinely in scope.

The children are where the detail goes. Each application's loop iteration comments on its own child as it completes — merge request opened, verifier passed, awaiting merge — so two applications remediated from one event do not interleave their history into a single unreadable timeline. The parent carries the event-level story: what was published, what TPA found, who owns each fix.

== The Merge Request the Agent Wrote

In the loop, the Orchestrator launches the `impact-analyzer` agent. The agent reads the application's `pom.xml`, bumps the dependency to the remediated `.rhlw` version, pushes a branch, and opens a merge request.

Open https://gitlab-gitlab.{openshift_cluster_ingress_domain}[GitLab^] and go to `acme-{guid}/benefits-mgmt-app` → *Merge requests*. The title follows a fixed shape:

[source,text]
----
[LW] 🔴 Bump h2 to 2.2.224.rhlw-70003 to fix CVE-2023-48795
----

That example is from a real `wire-transfer-svc` run — yours will name the dependency you just published. The coloured dot encodes severity, so a reviewer scanning a list of twenty merge requests can triage before opening any of them.

The diff itself is almost boring — the same single-line `pom.xml` change Renovate made in Module 2. The interesting part is the description, which is the artifact a human is actually expected to read:

[cols="1,3",options="header"]
|===
| Section | What it carries

| Summary
| Package, current version, remediated version, a link to the CVE, CVSS score, Lightwell risk score, and the SBOM impact

| Vulnerability Details
| What the CVE is and how the remediated build addresses it

| Automated Validation
| An eight-row table of checks. At this point every row reads `Pending` — nothing has been tested yet

| Risk Assessment
| The application's Acme Inc. risk class and the rationale from its policy file

| Recommended Action
| Derived, not guessed: a failed check means do not merge; a `HIGH` or `CRITICAL` risk class means human review even when everything passes
|===

image::gitlab-ai-mr-summary.png[AI-generated merge request showing the title and Summary table]

NOTE: The advisory data comes from a TPA lookup, not from the model. If your TPA has no advisory for the component, the Summary reads "not referenced" and "not scored" rather than a plausible-looking number. The agent is explicitly instructed not to invent security data — a fabricated CVSS score in an audit trail is worse than a blank one.

== The Pipeline Fills in the Validation Table

The merge request is created before any testing has happened, so every row in the *Automated Validation* table starts as `Pending`. A Pipelines-as-Code pipeline, `build-pull-request`, runs against the open merge request, executes `mvn verify` together with the CycloneDX SBOM plugin, and then rewrites that one section of the description with real results.

Refresh the merge request after a minute or two and the table will have filled in:

[cols="2,3",options="header"]
|===
| Check | What it actually measures

| Acme Inc. Risk Class
| The `riskClass` from the application's policy file

| Binary signature verification
| An *integrity* check — the published JAR is compared against the checksum Nexus recorded for it. The lab mirror ships no detached GPG signature, so this is not a cryptographic signature check and is labelled accordingly.

| SBOM integrity
| A CycloneDX SBOM is generated in the same build and asserted to list the bumped coordinate

| Unit tests
| `surefire` results from `mvn verify`

| Integration tests
| `failsafe` results from the same run

| Dependency compatibility
| Asserts that what the `pom.xml` declares is what the build actually resolved

| Regression scan
| *Not implemented.* This row stays `Pending`.

| License compliance
| Compares the licence declared by the base POM against the remediated POM, normalised so that equivalent phrasings do not raise a false alarm
|===

image::gitlab-ai-mr-validation-table.png[Automated Validation table in the merge request, filled in by the pipeline]

IMPORTANT: Six of those eight rows are measured. *Regression scan is not implemented* and renders as `Pending` — a behavioural diff would mean running the whole suite against the target-branch baseline as well, roughly doubling build time, and that call has not been made yet. Nothing here is ever reported green without having been measured, which is the only reason the table is worth putting in front of a reviewer at all.

== The Low-Risk Application Merges Itself

Back on the Orchestrator canvas, the *MR Verifier* node confirms the merge request is healthy and every check reported, then the *Auto-approve?* condition reads the approval value that travelled with the application's own policy.

For `benefits-mgmt-app` that value is `auto_approve`, so the canvas takes the green branch to *Merge MR (auto-approved)*. The Orchestrator undrafts the merge request and merges it. No human is asked, and no human is notified. The child incident gets a comment recording the merge, and the loop moves on to the next application.

Go back to GitLab and open the merge request. It is already merged, and the merge was performed by the automation account — you never touched it.

This is the volume case, and it is the whole economic argument for the platform. An internal HR application, a compatible rebuild of a library, every automated check green: there is no decision here that a person adds value to, so no person is asked. Multiply that by forty remediations a week and the time saved is not the merge click — it is the context switch that surrounds it.

[NOTE]
====
The decision is made from `.lightwell/policy.json` in the application's own repository, and it fails closed. If that file is missing, unreadable or malformed, the Orchestrator treats the application as `needs_approval` and routes it to a human. Nothing merges itself by accident.
====

== The Judgement Call

On the canvas, the *Auto-approve?* condition does not see `auto_approve`, so it takes the other branch: a comment on the child incident recording that the merge request is ready and *awaiting a GitLab merge*. Then the execution ends.

Read that again, because it is easy to misread as a failure. The Orchestrator has not crashed, timed out, or parked a job that is burning a worker somewhere. It has done everything it is permitted to do and stopped. The merge request is open in GitLab with your name on it, and nothing further happens in this entire platform until a person acts.

[IMPORTANT]
====
*The pause lives in GitLab, not in the Orchestrator.* There is no approve button on the canvas and no task in a queue waiting for you to tick it. The human gate is the merge request itself — the artifact that actually carries the evidence — rather than a prompt in an automation tool that quotes a ticket number at you.
====

Go and read the merge request in `acme-{guid}/wire-transfer-svc`. Everything you need is in one page:

* The diff — a single version bump in `pom.xml`, the upstream version unchanged
* The CVE and its CVSS score, pulled from TPA rather than from the model
* The validation table — unit tests, integration tests, SBOM integrity, licence compliance and dependency compatibility, all measured on this exact change
* The risk class, `HIGH`, with its rationale: payment-critical, PCI-scoped
* The recommended action, which says *human review required* precisely because the risk class is `HIGH` — not because anything failed

Read that last point again, because it is the whole argument. Every automated check passed. The platform still refused to merge it. The policy says that on a system that moves customer money a person signs off even on a change that looks perfect, and the platform is not allowed to talk itself out of that — not even with a full table of green ticks to point at.

Note also what the merge request is still marked as: *Draft*. The same verifier that undrafted the `benefits-mgmt-app` request left this one drafted on purpose, because its risk class demands a reviewer. The state of the merge request is itself part of the policy.

When you are satisfied, merge it yourself in GitLab.

That click is the only manual step in the entire module, and it is the one the whole design exists to protect. Everything up to it was preparation so that your decision is informed; everything after it is automation again.

From here it is the same spine as the low-risk application: merging fires the GitLab webhook, Event-Driven Ansible relays it, and a short Orchestrator run records the merge on the child incident. `build-push-to-main` builds, generates the SBOM, signs via Tekton Chains, pushes to the Nexus OCI registry and promotes the `imageTag` into `acme-deployment`; ArgoCD syncs and the new pod rolls out in `{user}-app`. Each stage reports back as it completes.

== The Incident Closes Last

Go back to the https://snow-mock-snow-{guid}.{openshift_cluster_ingress_domain}[ServiceNow mock^] tab you left open.

The parent incident is now *Resolved*, and the comment that resolved it is a rollup: what was published, which child incidents were raised, and where the per-application detail lives. Read the whole thread from the top. It is the complete history of the remediation, written as it happened:

. The incident was raised the moment Nexus announced the artifact — before anything was known about who was affected
. TPA's answer was recorded: which applications actually contain the component
. A child incident was opened for each one, and the classify result named who owns each fix
. Each child collected its own iteration comments as the agent worked
. Merge, build and deploy were each written in as they completed
. The parent resolved only once ArgoCD reported the application Healthy

Notice what resolved it. Not the merge, and not a green pipeline — the *deploy*. On the canvas, `SNOW finalize` hangs off the deploy branch, so the ticket stays open until the remediated code is actually running. A build that passes and never ships does not close anything.

That is also why the Orchestrator shows you several executions rather than one long-running job. The start execution ends when the merge requests are ready; merge, build and deploy each arrive later as webhooks and start their own short execution. The incident is what stitches them back into a single story — which is precisely the job a ticket is supposed to do.

NOTE: The child incidents stay open. Only the parent is resolved today; per-application close on deploy success has not been wired up yet. If you are demonstrating this to an auditor, show them the parent.

[TIP]
====
This is the slide that usually lands in front of a risk or compliance team. Nobody had to be asked for the evidence, and nobody had to assemble it afterwards. The incident was open before the change existed, it accumulated every decision and measurement along the way, and it closed when the fix was live — produced entirely as a side effect of doing the work.

You have just run the *Full Automation* path end to end:

. You published a remediated artifact; Nexus raised a `component CREATED` event

. TPA answered which applications were genuinely affected, from SBOM data
. Each application was classified against its own `.lightwell/policy.json`

. The parent incident resolved once ArgoCD reported the deployment Healthy, carrying a complete, timestamped trail

=== What This Actually Buys You

The difference from Path 1 is not "AI wrote the merge request". It is three things:

* *Scope* — the system knows which applications contain the component, because it asked TPA rather than scanning a single repository.
* *Evidence* — by the time a human looks at the change, the tests have run and the results are in the merge request. The reviewer reads measurements, not promises.
* *Proportionality* — attention is spent where it changes the outcome. An internal HR application merges itself. A PCI-scoped payment service does not, and no amount of green checkmarks changes that.

Scale is what makes this necessary. One remediation a week is a Renovate problem. Forty a week across sixty repositories, each needing a risk judgement and an audit trail, is an orchestration problem — and the only way a human stays in the loop at that volume is if the loop stops bothering them about `benefits-mgmt-app`.
