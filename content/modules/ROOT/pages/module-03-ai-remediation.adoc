= Module 3: Full Automation — AI-Driven Remediation
:navtitle: Module 3: AI Remediation (Path 2)

[WARNING]
====
This module is a *work in progress*. Steps and screenshots may change before the final version.
====

*Duration:* 30 minutes

Module 2 ended with a deliberate limitation: Renovate found one dependency in one repository and asked you to merge it. That works until the day Lightwell publishes forty remediations across sixty repositories, and "ask a human to merge it" stops being a strategy.

This module walks through *Path 2* — the same remediation event, handled by the platform instead of by you. An Automation Orchestrator workflow opens a ServiceNow incident, asks Trusted Profile Analyzer which applications are actually affected, applies each application's own approval policy, and dispatches an AI agent to write the merge request. The pipeline then tests the change and writes the results back into the merge request body, so that when a human *is* asked to decide, they are reading evidence rather than guessing.

You will remediate two of your three applications:

* `benefits-mgmt-app` — internal HR application, risk class `LOW`, policy `auto_approve`. The platform merges it without you.
* `wire-transfer-svc` — payment-critical and PCI-scoped, risk class `HIGH`, policy `needs_approval`. The platform does everything *except* the last step, and then waits for you.

That contrast is the point of the module. Automation is not about removing the human — it is about making sure the human is only interrupted when their judgement is actually worth something.

== What Changes Compared to Path 1

[cols="1,2,2",options="header"]
|===
| Stage | Path 1 (Module 2) | Path 2 (this module)

| Trigger
| Renovate polls Nexus on a schedule
| Nexus fires a `component CREATED` webhook the moment the artifact lands

| Who finds the affected apps
| Renovate reads one repository's `pom.xml`
| TPA is queried for every SBOM containing the component

| Who writes the fix
| Renovate's regex manager
| The `impact-analyzer` AI agent (OpenCode)

| What the merge request says
| A one-line version bump
| CVE, CVSS, risk class, and a validation table filled in by the pipeline

| Who approves
| Always you
| Per-app policy — `auto_approve` or `needs_approval`

| Audit trail
| Git history only
| A ServiceNow incident, commented at every stage

| Build, sign, deploy
| Shared — Tekton, Nexus OCI, ArgoCD, TPA
| Shared — identical
|===

The back half of both paths is the same. Path 2 only replaces *who decides what to change and whether it may ship*.

== The Orchestrated Pipeline

Event-Driven Ansible is deliberately thin here. It is a sensor: it recognises the `.rhlw` artifact event and launches one job template, `SDLC Start Orchestrator`, which posts to the Automation Orchestrator webhook. Everything after that is a node on the Orchestrator canvas, which means the whole flow is visible in one place and every step is recorded as it runs.

== Two Applications, Two Policies

Each repository carries a `.lightwell/policy.json` file. It is the only thing that decides whether a human is interrupted:

[cols="2,1,1,3",options="header"]
|===
| Application | `remediation_owner` | `approval` | `riskClass` and why

| `wire-transfer-svc`
| `ao`
| `needs_approval`
| `HIGH` — payment-critical, PCI-scoped system

| `benefits-mgmt-app`
| `ao`
| `auto_approve`
| `LOW` — internal HR application, no regulated data

| `report-generator-app`
| `renovate`
| —
| `LOW` — internal reporting tool, no regulated data
|===

The policy travels with the code, in the repository, reviewed like any other change. There is no approval matrix in a wiki that nobody has opened since the last audit.

TIP: Open `.lightwell/policy.json` in `acme-{guid}/wire-transfer-svc` in https://gitlab-gitlab.{openshift_cluster_ingress_domain}[GitLab^] before you start. It is four lines, and it is the entire governance model for this lab.

== The Merge Request the Agent Wrote

In the loop, the Orchestrator launches the `impact-analyzer` agent. The agent reads the application's `pom.xml`, bumps the dependency to the remediated `.rhlw` version, pushes a branch, and opens a merge request.

Open https://gitlab-gitlab.{openshift_cluster_ingress_domain}[GitLab^] and go to `acme-{guid}/benefits-mgmt-app` → *Merge requests*. The title follows a fixed shape:

[source,text]
----
[LW] 🔴 Bump h2 to 2.2.224.rhlw-70003 to fix CVE-2023-48795
----

That example is from a real `wire-transfer-svc` run — yours will name the dependency you just published. The coloured dot encodes severity, so a reviewer scanning a list of twenty merge requests can triage before opening any of them.

The diff itself is almost boring — the same single-line `pom.xml` change Renovate made in Module 2. The interesting part is the description, which is the artifact a human is actually expected to read:

[cols="1,3",options="header"]
|===
| Section | What it carries

| Summary
| Package, current version, remediated version, a link to the CVE, CVSS score, Lightwell risk score, and the SBOM impact

| Vulnerability Details
| What the CVE is and how the remediated build addresses it

| Automated Validation
| An eight-row table of checks. At this point every row reads `Pending` — nothing has been tested yet

| Risk Assessment
| The application's Acme Inc. risk class and the rationale from its policy file

| Recommended Action
| Derived, not guessed: a failed check means do not merge; a `HIGH` or `CRITICAL` risk class means human review even when everything passes
|===

== The Pipeline Fills in the Validation Table

The merge request is created before any testing has happened, so every row in the *Automated Validation* table starts as `Pending`. A Pipelines-as-Code pipeline, `build-pull-request`, runs against the open merge request, executes `mvn verify` together with the CycloneDX SBOM plugin, and then rewrites that one section of the description with real results.

Refresh the merge request after a minute or two and the table will have filled in:

[cols="2,3",options="header"]
|===
| Check | What it actually measures

| Acme Inc. Risk Class
| The `riskClass` from the application's policy file

| Binary signature verification
| An *integrity* check — the published JAR is compared against the checksum Nexus recorded for it. The lab mirror ships no detached GPG signature, so this is not a cryptographic signature check and is labelled accordingly.

| SBOM integrity
| A CycloneDX SBOM is generated in the same build and asserted to list the bumped coordinate

| Unit tests
| `surefire` results from `mvn verify`

| Integration tests
| `failsafe` results from the same run

| Dependency compatibility
| Asserts that what the `pom.xml` declares is what the build actually resolved

| Regression scan
| *Not implemented.* This row stays `Pending`.

| License compliance
| Compares the licence declared by the base POM against the remediated POM, normalised so that equivalent phrasings do not raise a false alarm
|===

// TODO screenshot: the Automated Validation table in the merge request
// description after `build-pull-request` has completed, showing the mix of

image::gitlab-ai-mr-validation-table.png[Automated Validation table in the merge request, filled in by the pipeline]

IMPORTANT: Six of those eight rows are measured. *Regression scan is not implemented* and renders as `Pending` — a behavioural diff would mean running the whole suite against the target-branch baseline as well, roughly doubling build time, and that call has not been made yet. Nothing here is ever reported green without having been measured, which is the only reason the table is worth putting in front of a reviewer at all.

== The Low-Risk Application Merges Itself

Back on the Orchestrator canvas, the *MR Verifier* node confirms the merge request is open and healthy, then the *Auto-approve?* condition reads the approval value that travelled with the application's policy.

For `benefits-mgmt-app` that value is `auto_approve`, so the canvas takes the auto branch straight to *Merge MR (auto)*. No human is asked. The incident gets an iteration comment recording the merge, and the loop moves on.

Go back to GitLab and confirm the merge request is already merged. You did not touch it.

This is the volume case. An internal HR application, a compatible rebuild of a library, every automated check green — there is no decision here that a person adds value to, so no person is asked.

== Build, Sign, Promote, Deploy

Merging to `main` starts the `build-push-to-main` pipeline. Open the OpenShift Console, navigate to *Pipelines* → *Pipelines*, select the *PipelineRuns* tab, and make sure the `build-{guid}` namespace is selected. You should see the run for `benefits-mgmt-app`:

. *Build* — compiles the application against the remediated dependency
. *Generate SBOM* — CycloneDX SBOM, uploaded to your TPA instance
. *Sign* — Tekton Chains signs the image via Trusted Artifact Signer, with no long-lived signing key
. *Push* — the signed image goes to the Nexus OCI registry
. *Promote* — `promote-to-deployment-repo` bumps the application's `imageTag` in the `acme-deployment` repository

== The Judgement Call

On the canvas, the *Auto-approve?* condition does not see `auto_approve`, so it routes to an approval node named *Approve remediation MR*. The Orchestrator is now waiting on a person. The prompt names the repository and the merge request number:

[source,text,subs=attributes+]
----
Approve merging the verified remediation MR for acme-{guid}/wire-transfer-svc (!1)?
----

The gate has a 24-hour decision window and, if nobody answers in that time, it falls back to *reject*. An unanswered approval does not quietly become a yes.

=== What This Actually Buys You

The difference from Path 1 is not "AI wrote the merge request". It is three things:

* *Scope* — the system knows which applications contain the component, because it asked TPA rather than scanning a single repository.
* *Evidence* — by the time a human looks at the change, the tests have run and the results are in the merge request. The reviewer reads measurements, not promises.
* *Proportionality* — attention is spent where it changes the outcome. An internal HR application merges itself. A PCI-scoped payment service does not, and no amount of green checkmarks changes that.

Scale is what makes this necessary. One remediation a week is a Renovate problem. Forty a week across sixty repositories, each needing a risk judgement and an audit trail, is an orchestration problem — and the only way a human stays in the loop at that volume is if the loop stops bothering them about `benefits-mgmt-app`.
